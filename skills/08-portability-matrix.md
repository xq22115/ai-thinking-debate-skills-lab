# 08 — 2026 Portability & Compatibility Matrix

Snapshot refreshed: 2026-08-18 evening, Asia/Singapore.

## Principle

Portable procedural knowledge and host-specific execution must be separated.

| Layer | Portable? | Notes |
|---|---:|---|
| Goal/acceptance contract | High | Plain structured text works everywhere |
| Claim/obligation graph | High | Runtime adapters differ, semantics should not |
| Evidence-gap workflow | High | Tool adapters differ |
| Competing hypotheses | High | Model/runtime independent |
| Debate topology | Medium–High | Parallelism APIs differ |
| Skill metadata | Medium | Field names/trigger semantics differ by host |
| Tool permissions | Low | Host-specific |
| Sandbox execution | Low | Runtime-specific |
| Durable state | Medium | Concept portable, implementation host-specific |
| MCP integration | Medium | Must target current protocol/version |
| Desktop automation | Low | Windows/macOS permissions differ |

## OpenAI Codex — plugin-first packaging

Current official Codex example repository: `openai/plugins`.

Observed current contract:
- each plugin requires `.codex-plugin/plugin.json`;
- optional companion surfaces include `skills/`, `.app.json`, `.mcp.json`, plugin-level `agents/`, `commands/`, `hooks.json`, and `assets/`;
- richer plugins combine skills with MCP/app/agent surfaces;
- the former `openai/skills` repository is explicitly deprecated and directs current work to `openai/plugins`.

Adapter rule:
Do not model current Codex delivery as a loose skill folder alone. Keep portable capability semantics separate, then wrap them in current plugin metadata and host-specific surfaces.

## OpenAI / Agents SDK

Current 2026 direction recovered elsewhere in this archive:
- model-native harness;
- native sandbox execution;
- externalized state;
- snapshot/rehydration;
- isolated subagent routing;
- 2026-08-18 upstream evidence further separates skill description from workflow/runtime execution.

Adapter rule:
Keep long-running state outside the transient model context and do not collapse skill, workflow, and execution harness into one abstraction.

## Anthropic / Agent Skills

Official public skills architecture:
- self-contained skill folders;
- `SKILL.md`;
- YAML frontmatter;
- scripts/references/assets when needed;
- progressive disclosure;
- Claude Code plugin-marketplace distribution is supported by the official skills repository;
- Anthropic explicitly advises testing skills in the target environment before critical use.

Adapter rule:
Keep the portable skill concise; push large references and deterministic scripts into bundled resources. Treat target-runtime verification as a separate release gate.

## Google ADK — 2.0 compatibility boundary

Official `google/adk-python` README observed updated 2026-08-13 identifies the current line as **Agent Development Kit (ADK) 2.0**.

Relevant 2.0 capabilities:
- graph-based workflow runtime;
- routing, fan-out/fan-in, loops, retry and dynamic nodes;
- explicit state and nested workflows;
- structured agent-to-agent Task API;
- modular multi-agent hierarchies;
- MCP/custom/OpenAPI tools;
- built-in evaluation/development surfaces.

Critical breaking-change boundary:
- ADK 2.0 changes the agent API, event model and session schema;
- sessions generated by ADK 2.0 are readable by ADK 1.28+ with extra fields ignored;
- older 1.x versions are not session-compatible.

Adapter rule:
Pin the ADK major/minor, record session-schema provenance, and never copy a 1.x orchestration example into a 2.0 deployment without migration review and runtime tests.

## MCP 2026-07-28

Key migration facts:
- stateless protocol core;
- no protocol-level session as the central model;
- MRTR;
- extension framework;
- Tasks as an extension;
- authorization hardening;
- formal deprecation policy.

Adapter rule:
Do not reuse old session assumptions blindly. Explicit application state handles are safer than hidden transport state.

## OpenClaw

Because the project changes rapidly:
- pin exact release/commit for production;
- validate skill/plugin contracts against the installed version;
- do not copy configuration from older chats without compatibility checks;
- retain context-limit provenance and ownership through resume/finalization where supported.

## Windows

Validate:
- shell differences (PowerShell/cmd/bash);
- path separators and quoting;
- filesystem permissions;
- service/task scheduler behavior;
- desktop app sandbox/security restrictions;
- WSL boundary if used.

## macOS

Validate:
- app sandbox/TCC permissions;
- launchd vs Windows scheduler;
- shell defaults;
- filesystem case sensitivity assumptions;
- Keychain/credential integration.

## Compatibility declaration template

Every deployable skill/config should state:

```yaml
compatibility:
  hosts:
    - name: <host>
      min_version: <version-or-date>
      status: supported|experimental|unsupported
  os:
    windows: supported|experimental|unsupported
    macos: supported|experimental|unsupported
    linux: supported|experimental|unsupported
  required_tools: []
  required_permissions: []
  tested_on: []
  last_verified: YYYY-MM-DD
```

## Hard release rule

`PORTABLE_SPEC_COMPLETE != RUNTIME_ADAPTER_VERIFIED`

Never claim “cross-platform” or “current-version compatible” without target-runtime evidence.
