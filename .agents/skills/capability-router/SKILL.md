# Capability Router

## Purpose
Choose the smallest verified capability portfolio that can reach the user's acceptance state without loading or installing unnecessary machinery.

## Activate when
Use for multi-tool work, capability discovery, local-vs-remote route choice, fallback selection or when a named mechanism may not be the only valid way to satisfy the goal.

## Do not activate
Do not invoke merely because many tools exist. Do not replace an explicitly required mechanism with an easier substitute.

## Antigravity-native execution
Prefer already-visible native workspace/file/terminal skills and verified MCP tools. Route by target fit, health, permission, reversibility, evidence quality and acceptance coverage—not by product familiarity.

## Workflow
1. Compile required capabilities from acceptance tests.
2. Inventory currently visible and authorized primitives.
3. Map candidate routes to uncovered requirements.
4. Probe the cheapest uncertain dependency.
5. Select a bounded portfolio; acquire only missing capabilities.
6. Preserve fallback and rollback paths.

## Validation
For every selected route record visibility, authorization, invocation evidence and the criterion it closes. A configured connector or skill file does not count as live capability.

## Boundaries
Routing cannot create tools, permissions or provider entitlements. Keep host-specific installation/authentication in adapters/config, not inside portable task semantics.
